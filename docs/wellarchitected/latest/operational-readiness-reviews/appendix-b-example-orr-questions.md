# Appendix B: Example ORR questions

These are a few example questions that you can use to get started building your own ORR
program.

## Architecture

| What have you included in your architectural design to reduce the blast radius of<br>failures? |
| ---------------------------------------------------------------------------------------------- |
|                                                                                                |

| Please provide a table enumerating all customer impacting APIs, an explanation for what<br>each does, and the components and dependencies of your service that it touches. Include all<br>APIs whether they are public or private from the customer’s perspective. |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
|                                                                                                                                                                                                                                                                    |

| Please construct a failure model listing soft and hard failure modes for each of your<br>components and dependencies.                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Guidance**<br>Your failure model should include columns for **Component\*<br>• or **Dependency**, **Failure Type**, **Service<br>Impact**, and **Customer Impact\*\*.<br>Please address an outage of your service in its largest blast radius unit, such<br>as a cell, an Availability Zone (AZ), or a Region, plus a total infrastructure<br>outage in its largest blast radius (an AZ). |

| What is the retry and back-off strategy for each of your dependencies?                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Guidance**<br>For dependency calls made within the context of a synchronous API call, you<br>should generally retry once immediately, then give up.<br>For dependency calls made within the context of work requested through an<br>asynchronous API call, you should generally [exponentially<br>back off and retry with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/ "https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/") for retryable failures. |

| Have you intentionally set appropriate retry and socket timeout configuration for all<br>SDK usage?                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Guidance**<br>Not setting the [appropriate retry and<br>timeout logic](../../../sdkref/latest/guide/feature-retry-behavior.md "../../../sdkref/latest/guide/feature-retry-behavior.md") for your AWS SDK clients can lead to a thread pool with<br>all threads engaged in dependency operations. It's better to fail fast and a return<br>a response to the client for dependency calls made within the context of sync calls<br>from customers to let the client decide how and when to retry then timeout customer<br>requests. |

| What throttling techniques are you using to defensively protect your service from<br>customers?                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Guidance**<br>See [Fairness in multi-tenant<br>systems](https://aws.amazon.com/builders-library/fairness-in-multi-tenant-systems "https://aws.amazon.com/builders-library/fairness-in-multi-tenant-systems")<br>Are you using distributed throttling on your front-end?<br>Do you have pre-authentication throttles?<br>Are limits on request size enforced before authentication? |

| If your service was temporarily deactivated or shut down, what is your recovery time<br>objective (RTO) for restarting your service?                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Guidance**<br>Have you practiced it? Do you have a runbook for restarting your service? Are<br>there any off-box dependencies that are mandatory for restart? Have you confirmed<br>that there are no circular dependencies? |

## Release quality

| Do your customer impacting deployments automatically rollback incorrect deployments<br>before they breach your internal SLAs?                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | --------- |
| **Guidance**<br>AWS CodeDeploy: [Automatic Rollback on Amazon CloudWatch Alarm](../../../codedeploy/latest/userguide/deployments-rollback-and-redeploy.md#deployments-rollback-and-redeploy-automatic-rollbacks "../../../codedeploy/latest/userguide/deployments-rollback-and-redeploy.md#deployments-rollback-and-redeploy-automatic-rollbacks")<br>AWS Lambda: Possible with [Traffic Shifting<br>using CodeDeploy](../../../lambda/latest/dg/automating-updates-to-serverless-apps.md "../../../lambda/latest/dg/automating-updates-to-serverless-apps.md"), supported in [Serverless<br>Application Model](https://github.com/awslabs/serverless-application-model "https://github.com/awslabs/serverless-application-model"). Specify a list of CloudWatch Alarms in the<br>`DeployPreference` property [Lambda deployments with Automatic Rollback](https://github.com/awslabs/serverless-application-model/blob/master/docs/safe_lambda_deployments.rst#traffic-shifting-using-codedeploy "https://github.com/awslabs/serverless-application-model/blob/master/docs/safe_lambda_deployments.rst#traffic-shifting-using-codedeploy").<br>☐ Yes | No Risk<br>☐ No | High Risk |

| Do your customer impacting deployments run on-host validation tests to verify that the<br>software has started successfully and is responding correctly to health checks on<br>`localhost` before reregistering with the load balancer?                                                                                                                                                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | ----------------------------- |
| **Guidance**<br>CodeDeploy: Write validation scripts and execute them from the<br>`ValidateService`<br>[lifecycle event hook](../../../codedeploy/latest/userguide/reference-appspec-file-structure-hooks.md#reference-appspec-file-structure-hooks-list "../../../codedeploy/latest/userguide/reference-appspec-file-structure-hooks.md#reference-appspec-file-structure-hooks-list")<br>Lambda: Select Not Applicable<br>☐ Yes | No Risk<br>☐ No | High Risk<br>☐ Not Applicable |

| Do you have a mechanism in place to ensure all code changes (software, configuration,<br>infrastructure, canary, and ops tools) to production systems are reviewed and approved by<br>someone other than the code author?                                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | --------- |
| **Guidance**<br>You may choose to add a [manual approval<br>action](../../../codepipeline/latest/userguide/approvals-action-add.md "../../../codepipeline/latest/userguide/approvals-action-add.md") into your AWS CodePipeline pipelines and limit permissions to a set of<br>approvers.<br>☐ Yes | No Risk<br>☐ No | High Risk |

| What is your load test plan?                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Guidance**<br>You should assume that you will find the breaking point of your service multiple<br>times, iteratively addressing uncovered performance bottlenecks and repeating the<br>load test. It should consider a small number of very large customers, a large number<br>of very small customers, and sinusoidal load.<br>Conduct a load test that simulates a surge of traffic from a single customer to<br>validate behavior under this kind of load. Conduct one large scale load test against<br>your production environment (a) before you launch, and (b) subsequently during each<br>quarter, to validate proper scaling as you grow (or for any potential peak usage). |

| Do you publish your canary synthetics errors to an independent metric? Subsequently, do<br>you alarm on this metric?                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | --------- |
| **Guidance**<br>Ensure that your canary synthetics errors are published to their own metrics, as<br>opposed to being combined with all errors. This allows your service to alarm on an<br>individual canary error rate.<br>☐ Yes | No Risk<br>☐ No | High Risk |
