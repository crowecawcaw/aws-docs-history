

# Learn and evolve from events

 Learn, share, and continuously improve to sustain operational excellence. Dedicate work cycles to making continual incremental improvements. Perform post-incident analysis of all customer-impacting events. Identify the contributing factors and preventive action to limit or help prevent recurrence. Communicate contributing factors with affected communities as appropriate. Regularly evaluate and prioritize opportunities for improvement (for example, feature requests, issue remediation, and compliance requirements), including both the workload and operations procedures. 

 Include feedback loops within your procedures to rapidly identify areas for improvement and capture learnings from running operations. Keep what you learn in a searchable knowledge repository with clear ownership and a review cadence, so lessons stay findable and current instead of living in individual memory. Where a documented procedure diverges from what people actually do, treat the document as the defect and route the correction back to the runbook or playbook it belongs to. Share lessons learned across teams so the benefit is not confined to the team that earned it. Analyze trends within lessons learned and perform cross-team retrospective analysis of operations metrics to identify opportunities and methods for improvement. Implement changes intended to bring about improvement and evaluate the results to determine success.

## Capability intent
<a name="ops07-intent"></a>
+  Every customer-impacting event is followed by a consistent, blameless post-incident analysis that identifies the multiple contributing factors, not a single root cause. 
+  Findings become tracked corrective actions with named human ownership, shared across teams so the benefit is not confined to one team. 
+  Improvement opportunities are classified and prioritized with consistent criteria tied to cost, risk, and customer experience, including the partial failures internal metrics miss. 
+  Knowledge lives in a single searchable repository with clear ownership and a review cadence, with one authoritative page per procedure. 
+  When a documented procedure diverges from practice, the document is treated as the defect and the correction is routed back to the procedure it belongs to. 

## Common issues to watch for
<a name="ops07-issues"></a>
+  Incidents are closed once service is restored, with no analysis, so the same failure recurs. 
+  Post-incident analysis looks for a single root cause and assigns blame, which hides contributing factors and discourages candor. 
+  Corrective actions are identified but not tracked or owned, so they are never completed. 
+  Improvement work is prioritized by whoever asks loudest rather than by business impact, and partial failures that customers feel go unaddressed. 
+  Knowledge accumulates as volume across many stale pages, so responders cannot find the one authoritative answer.
