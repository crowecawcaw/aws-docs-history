| **[Standard<br>queues](standard-queues.md "standard-queues.md")**Standard queues support a very high, nearly unlimited number of API calls per second, per action<br>([`SendMessage`](../APIReference/API_SendMessage.md "../APIReference/API_SendMessage.md"), [`ReceiveMessage`](../APIReference/API_ReceiveMessage.md "../APIReference/API_ReceiveMessage.md"), While standard queues scale automatically with demand, it is essential to monitor usage patterns to ensure optimal performance, especially in regions with higher workloads. |
| **[FIFO queues](sqs-fifo-queues.md "sqs-fifo-queues.md")**<br>• Each partition in a FIFO queue is limited to 300 transactions per second, per<br>API action (`SendMessage`, `ReceiveMessage`, and<br>`DeleteMessage`). This limit applies specifically to non-high<br>throughput mode. By switching to high throughput mode, you can surpass this<br>default limit. To<br>enable high-throughput mode, see [Enabling high throughput for FIFO queues in<br>Amazon SQS](enable-high-throughput-fifo.md "enable-high-throughput-fifo.md").<br>• If you use batching, non-high throughput FIFO queues support up to 3,000<br>messages per second, per API action (`SendMessage`,<br>`ReceiveMessage`, and `DeleteMessage`). The 3,000 messages<br>per second represent 300 API calls, each with a batch of 10 messages.<br>**[High throughput for<br>FIFO queues](high-throughput-fifo.md "high-throughput-fifo.md")**<br>Amazon SQS FIFO limits are based on the number of API requests, not message limits. For<br>high throughput mode, these API request limits are as follows:<br>**Transaction throughput limits (Non-batching API<br>calls)**<br>These limits define how frequently each API operation (such as [SendMessage](../APIReference/API_SendMessage.md "../APIReference/API_SendMessage.md"), [ReceiveMessage](../APIReference/API_ReceiveMessage.md "../APIReference/API_ReceiveMessage.md"), or [DeleteMessage](../APIReference/API_DeleteMessage.md "../APIReference/API_DeleteMessage.md")) can be performed independently, ensuring efficient system<br>performance within the allowed transactions per second (TPS).<br>The following limits are based on non-batched API calls:<br>• US East (N. Virginia), US West (Oregon), and Europe (Ireland): Up to 70,000<br>transactions per second (TPS).<br>• US East (Ohio) and Europe (Frankfurt): Up to 19,000 TPS.<br>• Asia Pacific (Mumbai), Asia Pacific (Singapore), Asia Pacific (Sydney), and<br>Asia Pacific (Tokyo): Up to 9,000 TPS.<br>• Europe (London) and South America (São Paulo): Up to 4,500 TPS.<br>• All other AWS Regions: Default throughput of 2,400 TPS.<br>**Maximizing throughput with batching**<br>Processes multiple messages in a single API call, which significantly increasing<br>efficiency. Instead of handling each message individually, batching allows you to<br>send, receive, or delete up to 10 messages in a single API request. This reduces the<br>total number of API calls, allowing you to process more messages per second while<br>staying within the transaction limits (TPS) for the region, maximizing throughput and<br>system performance. For more information, see [Increasing throughput<br>using horizontal scaling and action batching with Amazon SQS](sqs-throughput-horizontal-scaling-and-batching.md "sqs-throughput-horizontal-scaling-and-batching.md").<br>The following limits are based on batched API calls:<br>• US East (N. Virginia), US West (Oregon), and Europe (Ireland): Up to 700,000<br>messages per second (10x the non-batch limit of 70,000 TPS).<br>• US East (Ohio) and Europe (Frankfurt): Up to 190,000 messages per<br>second.<br>• Asia Pacific (Mumbai), Asia Pacific (Singapore), Asia Pacific (Sydney), and<br>Asia Pacific (Tokyo): Up to 90,000 messages per second.<br>• Europe (London) and South America (São Paulo): Up to 45,000 messages per<br>second.<br>• All other AWS Regions: Up to 24,000 messages per second.<br>**Optimizing throughput beyond batching**<br>While batching can greatly increase throughput, it’s important to consider other<br>strategies for optimizing FIFO performance:<br>• **Distribute messages across multiple message group<br>IDs\*<br>• – Since messages within a single group are processed<br>sequentially, distributing your workload across multiple message groups allows for<br>better parallelism and higher overall throughput. For more information, see [Partitions and data distribution for high<br>throughput for SQS FIFO queues](high-throughput-fifo.md#partitions-and-data-distribution "high-throughput-fifo.md#partitions-and-data-distribution").<br>• **Efficient use of API calls** – Minimize<br>unnecessary API calls, such as frequent visibility changes or repeated message<br>deletions, to optimize the use of your available TPS and improve<br>efficiency.<br>• **Use long poll receives** – Utilize long polling<br>by setting [`WaitTimeSeconds`](../APIReference/API_ReceiveMessage.md#SQS-ReceiveMessage-request-WaitTimeSeconds "../APIReference/API_ReceiveMessage.md#SQS-ReceiveMessage-request-WaitTimeSeconds") in your receive requests to reduce empty<br>responses when no messages are available, lowering unnecessary API calls and<br>making better use of your TPS quota.<br>• **Requesting throughput increases\*\* – If<br>your application requires throughput higher than the default limits, request an increase<br>using the [Service Quotas](https://console.aws.amazon.com/servicequotas/home/services/sqs/quotas "https://console.aws.amazon.com/servicequotas/home/services/sqs/quotas") console. This can be necessary for high-demand workloads<br>or in regions with lower default limits. To<br>enable high-throughput mode, see [Enabling high throughput for FIFO queues in<br>Amazon SQS](enable-high-throughput-fifo.md "enable-high-throughput-fifo.md"). |
