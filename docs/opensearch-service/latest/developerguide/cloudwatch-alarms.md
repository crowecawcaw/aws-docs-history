# Recommended CloudWatch alarms for Amazon OpenSearch Service

CloudWatch alarms perform an action when a CloudWatch metric exceeds a specified value for
some amount of time. For example, you might want AWS to email you if your cluster
health status is `red` for longer than one minute. This section includes
some recommended alarms for Amazon OpenSearch Service and how to respond to them.

You can automatically deploy these alarms using AWS CloudFormation. For a sample stack, see the
related [GitHub
repository](https://github.com/ev2900/OpenSearch_CloudWatch_Alarms "https://github.com/ev2900/OpenSearch_CloudWatch_Alarms").

###### Note

If you deploy the CloudFormation stack, the `KMSKeyError` and
`KMSKeyInaccessible` alarms will exists in an `Insufficient
 Data` state because these metrics only appear if a domain encounters a
problem with its encryption key.

For more information about configuring alarms, see [Creating Amazon CloudWatch
Alarms](../../../AmazonCloudWatch/latest/monitoring/AlarmThatSendsEmail.md "../../../AmazonCloudWatch/latest/monitoring/AlarmThatSendsEmail.md") in the _Amazon CloudWatch User Guide_.

## Other alarms you might consider

Consider configuring the following alarms depending on which OpenSearch Service features you
regularly use.

| Alarm                                                                                | Issue                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WarmFreeStorageSpace` is >= 10%                                                     | You have reached 10% of your total free warm storage.<br>`WarmFreeStorageSpace` measures the sum of your<br>free warm storage space in MiB. UltraWarm uses Amazon S3 rather than<br>attached disks.                                                                                                                              |
| `HotToWarmMigrationQueueSize` is >= 20 for 1<br>minute, 3 consecutive times          | A high number of indexes are concurrently moving from hot<br>to UltraWarm storage. Consider scaling your cluster.                                                                                                                                                                                                                |
| `HotToWarmMigrationSuccessLatency` is >= 1 day, 1<br>consecutive time                | Configure this alarm so that you're notified if the<br>`HotToWarmMigrationSuccessCount` x latency is<br>greater than 24 hours if you’re trying to roll daily<br>indexes.                                                                                                                                                         |
| `WarmJVMMemoryPressure` maximum is >= 95% for 1<br>minute, 3 consecutive times       | The cluster could encounter out of memory errors<br>if usage increases. Consider scaling vertically.<br>OpenSearch Service uses half of an instance's RAM for the Java heap, up to a heap size of 32 GiB. You can scale instances vertically up to 64 GiB of RAM, at which point you can scale horizontally by adding instances. |
| `WarmOldGenJVMMemoryPressure` maximum is >= 80%<br>for 1 minute, 3 consecutive times |
| `WarmToColdMigrationQueueSize` is >= 20 for 1<br>minute, 3 consecutive times         | A high number of indexes are concurrently moving from<br>UltraWarm to cold storage. Consider scaling your cluster.                                                                                                                                                                                                               |
| `HotToWarmMigrationFailureCount` is >= 1 for 1<br>minute, 1 consecutive time         | Migrations might fail during snapshots, shard relocations,<br>or force merges. Failures during snapshots or shard<br>relocation are typically due to node failures or S3<br>connectivity issues. Lack of disk space is usually the<br>underlying cause of force merge failures.                                                  |
| `WarmToColdMigrationFailureCount` is >= 1 for 1<br>minute, 1 consecutive time        | Migrations usually fail when attempts to migrate index<br>metadata to cold storage fail. Failures can also happen when the<br>warm index cluster state is being removed.                                                                                                                                                         |
| `WarmToColdMigrationLatency` is >= 1 day, 1<br>consecutive time                      | Configure this alarm so that you're notified if the<br>`WarmToColdMigrationSuccessCount` x latency<br>is greater than 24 hours if you’re trying to roll daily<br>indexes.                                                                                                                                                        |
| `AlertingDegraded` is >= 1 for 1 minute, 1<br>consecutive time                       | Either the alerting index is red, or one or more nodes is<br>not on schedule.                                                                                                                                                                                                                                                    |
| `ADPluginUnhealthy` is >= 1 for 1 minute, 1<br>consecutive time                      | The anomaly detection plugin isn't functioning properly,<br>either because of high failure rates or because one of the<br>indexes being used is red.                                                                                                                                                                             |
| `AsynchronousSearchFailureRate` is >= 1 for 1<br>minute, 1 consecutive time          | At least one asynchronous search failed in the last<br>minute, which likely means the coordinator node failed. The<br>lifecycle of an asynchronous search request is managed<br>solely on the coordinator node, so if the coordinator goes<br>down, the request fails.                                                           |
| `AsynchronousSearchStoreHealth` is >= 1 for 1<br>minute, 1 consecutive time          | The health of the asynchronous search response store in<br>the persisted index is red. You might be storing large<br>asynchronous responses, which can destabilize a cluster. Try<br>to limit your asynchronous search responses to 10 MB or<br>less.                                                                            |
| `SQLUnhealthy` is >= 1 for 1 minute, 3 consecutive<br>times                          | The SQL plugin is returning 5\*xx<br>• response codes or passing invalid query<br>DSL to OpenSearch. Troubleshoot the requests that your<br>clients are making to the plugin.                                                                                                                                                    |
| `LTRStatus.red` is >= 1 for 1 minute, 1<br>consecutive time                          | At least one of the indexes needed to run the Learning to<br>Rank plugin has missing primary shards and isn't<br>functional.                                                                                                                                                                                                     |
