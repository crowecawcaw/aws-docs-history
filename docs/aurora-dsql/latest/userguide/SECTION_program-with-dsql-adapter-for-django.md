

# Aurora DSQL adapter for Django
<a name="SECTION_program-with-dsql-adapter-for-django"></a>

The Amazon Aurora DSQL adapter for Django (`aurora-dsql-django`) integrates Django object-relational mapping (ORM) with Aurora DSQL. It handles IAM authentication, Secure Sockets Layer (SSL) configuration, DDL generation differences (async indexes, identity/sequence columns), and connection management, so you can use the full Django ORM against a distributed Aurora DSQL cluster with minimal configuration. For more information, see the [Aurora DSQL adapter for Django](https://github.com/awslabs/aurora-dsql-orms/tree/main/python/django) and the [Django pet clinic example application](https://github.com/awslabs/aurora-dsql-orms/tree/main/python/django/examples/pet-clinic-app) on the GitHub website.

## About the adapter
<a name="SECTION_program-with-dsql-adapter-for-django-about-the-adapter"></a>

Amazon Aurora DSQL is a serverless, distributed relational database service optimized for transactional workloads. Aurora DSQL has specific requirements, including IAM-based authentication and asynchronous index creation. Aurora DSQL supports foreign key constraints enforced through optimistic concurrency control (OCC): foreign key (FK) conflicts raise a serialization error that your application can retry. As of v0.7.0, the Django adapter enables `supports_foreign_keys = True` and emits `REFERENCES` constraints in migrations and DDL.

With the Aurora DSQL adapter for Django, you can use the full Django ORM against Aurora DSQL without manually accounting for its behavioral differences. The adapter addresses these requirements by customizing the Django database backend.

### What is Aurora DSQL authentication?
<a name="SECTION_program-with-dsql-adapter-for-django-what-is-aurora-dsql-authentication"></a>

In Aurora DSQL, authentication involves:
+ **IAM authentication:** All connections use IAM-based authentication with time-limited tokens.
+ **Token generation:** The connector generates authentication tokens from your AWS credentials. Tokens have configurable lifetimes.

The Aurora DSQL adapter for Django automatically generates IAM authentication tokens when establishing connections, using the `aurora-dsql-python-connector`.

### Features
<a name="SECTION_program-with-dsql-adapter-for-django-features"></a>

The adapter provides the following features:
+ **Automatic IAM authentication** – Generates IAM tokens automatically for each connection from your AWS credentials.
+ **SSL** – Configure SSL through `OPTIONS`. The adapter supports the `require` and `verify-full` modes.
+ **UUID primary keys** – `AutoField` and `BigAutoField` map to universally unique identifier (UUID) columns with a `gen_random_uuid()` default.
+ **Sequence and identity keys** – Opt-in integer primary keys use `GENERATED BY DEFAULT AS IDENTITY`.
+ **Async index creation** – Creates all indexes with `CREATE INDEX ASYNC`.
+ **Foreign key support** – `supports_foreign_keys = True`, so migrations emit `REFERENCES` constraints with OCC-based enforcement. For the foreign key options that Aurora DSQL supports, see [Working with foreign key constraints in Aurora DSQL](working-with-foreign-key-constraints.md).
+ **OCC error handling** – Surfaces `OC000` (data conflict) and `OC001` (schema conflict) so that your application can retry.
+ **Django compatibility** – Works with Django 4.2 long-term support (LTS), 5.0, 5.1, and 5.2 LTS.

## Prerequisites
<a name="SECTION_program-with-dsql-adapter-for-django-prerequisites"></a>

Before you use the adapter, make sure that you have the following:
+ Python 3.10 or higher
+ Django 4.2 or higher
+ `psycopg` (v3) or `psycopg2`
+ AWS credentials with `dsql:DbConnectAdmin` permission (admin) or `dsql:DbConnect` (non-admin)

## Installation
<a name="SECTION_program-with-dsql-adapter-for-django-installation"></a>

## Configuration
<a name="SECTION_program-with-dsql-adapter-for-django-configuration"></a>

### `settings.py` — minimal
<a name="SECTION_program-with-dsql-adapter-for-django-settings-py-minimal"></a>

In the following example, replace {{cluster-id}} and {{region}} with the values for your cluster, and `admin` with your database user.

```
DATABASES = {
    'default': {
        'ENGINE': 'aurora_dsql_django',
        'HOST':   '{{cluster-id}}.dsql.{{region}}.on.aws',
        'USER':   'admin',
        'NAME':   'postgres',
        'OPTIONS': {
            'sslmode': 'verify-full',
        }
    }
}
```

With `verify-full`, the adapter defaults to `sslrootcert="system"`, which requires libpq 16 or later. On Linux, the `psycopg[binary]` and `psycopg2-binary` wheels also can't locate the system trust store, so set the `SSL_CERT_FILE` environment variable to your certificate authority (CA) bundle. Alternatively, pass the bundle path as `sslrootcert`, as shown in the next example. This works with any libpq version.

### `settings.py` — with a custom certificate bundle
<a name="SECTION_program-with-dsql-adapter-for-django-settings-py-with-certificate-verification"></a>

```
DATABASES = {
    'default': {
        'ENGINE': 'aurora_dsql_django',
        'HOST':   '{{cluster-id}}.dsql.{{region}}.on.aws',
        'USER':   'admin',
        'NAME':   'postgres',
        'OPTIONS': {
            'sslmode':    'verify-full',
            'sslrootcert': '/path/to/cert.pem',  # omit to use the system trust store
        }
    }
}
```

### `settings.py` — optional parameters
<a name="SECTION_program-with-dsql-adapter-for-django-settings-py-optional-parameters"></a>

The following table describes the keys that you can set inside the `OPTIONS` dictionary.


| Key | Default | Description | 
| --- | --- | --- | 
| sslmode | libpq default (prefer) | SSL verification level. Aurora DSQL requires TLS. Use verify-full for production. require encrypts the connection without verifying the certificate, so use it only outside production. | 
| sslrootcert | system CA | Path to CA certificate for verify-full | 
| profile | default credential chain | AWS profile name for credential resolution | 
| token\_duration\_secs | 60 | IAM token lifetime in seconds (connector default) | 

The following table describes the top-level keys of the database dictionary. Set these keys alongside `ENGINE` and `HOST`, not inside `OPTIONS`.


| Key | Default | Description | 
| --- | --- | --- | 
| USE\_SEQUENCE\_AUTOFIELDS | False | If True, AutoField/BigAutoField use IDENTITY columns instead of UUID | 
| SEQUENCE\_CACHE\_SIZE | 65536 | Cache size used when USE\_SEQUENCE\_AUTOFIELDS is True | 

## Primary key strategies
<a name="SECTION_program-with-dsql-adapter-for-django-primary-key-strategies"></a>

### UUID (default — recommended)
<a name="SECTION_program-with-dsql-adapter-for-django-uuid-default-recommended"></a>

```
import uuid
from django.db import models

class Owner(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    name = models.CharField(max_length=30)
    city = models.CharField(max_length=80)
```

`uuid.uuid4` generates the UUID client-side before the INSERT. When you keep the default `AutoField` or `BigAutoField` (no explicit `id` field), the adapter uses server-generated UUIDs (`gen_random_uuid()`).

### Identity / sequence keys (opt-in)
<a name="SECTION_program-with-dsql-adapter-for-django-identity-sequence-keys-opt-in"></a>

Enable in `settings.py`:

```
DATABASES = {
    'default': {
        'ENGINE': 'aurora_dsql_django',
        # ...
        'USE_SEQUENCE_AUTOFIELDS': True,
        'SEQUENCE_CACHE_SIZE': 65536,
    }
}
```

With this flag set, `AutoField` and `BigAutoField` generate `BIGINT GENERATED BY DEFAULT AS IDENTITY (CACHE 65536)` columns instead of UUID.

### `SequenceAutoField` (per-model explicit sequences)
<a name="SECTION_program-with-dsql-adapter-for-django-sequenceautofield-per-model-explicit-sequences"></a>

```
from aurora_dsql_django import SequenceAutoField

class Owner(models.Model):
    id = SequenceAutoField(primary_key=True)
    name = models.CharField(max_length=30)
```

## Defining models
<a name="SECTION_program-with-dsql-adapter-for-django-defining-models"></a>

### Foreign key fields
<a name="SECTION_program-with-dsql-adapter-for-django-foreign-key-fields"></a>

Aurora DSQL supports foreign key constraints with OCC-based enforcement — conflicts raise a serialization error (`OC000` / `SQLSTATE 40001`) that your application can retry — and supports `NO ACTION`, `RESTRICT`, `CASCADE`, `SET NULL`, `SET DEFAULT`, `MATCH SIMPLE`, `MATCH FULL`, and deferrable foreign keys.

Django generates `REFERENCES` constraints in migrations. Define FK fields normally — `db_constraint=True` (the default):

```
class Pet(models.Model):
    id    = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    name  = models.CharField(max_length=30)
    owner = models.ForeignKey(Owner, on_delete=models.CASCADE, null=True)
```

When adding FK constraints to existing tables, the adapter automatically issues `ALTER TABLE ... ADD CONSTRAINT ... NOT VALID` followed by `ALTER TABLE ASYNC ... VALIDATE CONSTRAINT` — you don't need to run these manually.

For CHECK constraints added via `ALTER TABLE`, the adapter issues the `NOT VALID` and `VALIDATE CONSTRAINT` calls, but the migration doesn't wait for the async validation job. Check the corresponding job in `sys.jobs` promptly and confirm that it succeeded. The constraint becomes valid only after the job succeeds.

**Important**  
To add an FK column to an existing table, add the column with `null=True`, backfill all rows, and keep the column nullable. Adding the column as non-nullable raises `NotSupportedError`. The following example shows the supported steps:  

```
# Step 1: add as nullable — this succeeds
owner = models.ForeignKey(Owner, on_delete=models.CASCADE, null=True)
# Step 2: backfill owner_id for existing rows; keep the column nullable
```

### Many-to-many relationships — use a custom intermediate table
<a name="SECTION_program-with-dsql-adapter-for-django-many-to-many-relationships-use-a-custom-intermediate-table"></a>

Define the intermediate table explicitly rather than relying on Django's auto-generated one. An explicit through-model gives you full control over the primary key type, ensuring it's compatible with Aurora DSQL:

```
class VetSpecialties(models.Model):
    id        = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    vet       = models.ForeignKey('Vet', on_delete=models.CASCADE)
    specialty = models.ForeignKey('Specialty', on_delete=models.CASCADE)

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=['vet', 'specialty'], name='unique_vet_specialty'),
        ]

class Vet(models.Model):
    id          = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    name        = models.CharField(max_length=30)
    specialties = models.ManyToManyField('Specialty', through='VetSpecialties')
```

### One-to-one relationships
<a name="SECTION_program-with-dsql-adapter-for-django-one-to-one-relationships"></a>

```
class Vet(models.Model):
    id    = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    name  = models.CharField(max_length=30)
    owner = models.OneToOneField(
        Owner,
        on_delete=models.SET_DEFAULT,
        null=True, blank=True, default=None
    )
```

## OCC retry pattern
<a name="SECTION_program-with-dsql-adapter-for-django-occ-retry-pattern"></a>

Aurora DSQL uses optimistic concurrency control (OCC). Conflicting concurrent transactions raise a `django.db.Error` with one of two error codes — `OC000` (data conflict: two transactions modified the same row) or `OC001` (schema conflict: cached schema catalog is out of date). Wrap write views in a retry decorator:

```
import random
import time
from django.db import Error

OCC_SQLSTATE = "40001"

def _is_occ_error(exc):
    # Django wraps the driver exception; the original lives in __cause__
    cause = getattr(exc, "__cause__", None) or getattr(exc, "__context__", None)
    return (
        getattr(cause, "sqlstate", None) == OCC_SQLSTATE   # psycopg (v3)
        or getattr(cause, "pgcode", None) == OCC_SQLSTATE  # psycopg2
    )

def with_retries(retries=3, initial_wait=1, delay_factor=2):
    def decorator(view):
        def wrapper(*args, **kwargs):
            delay = initial_wait
            for attempt in range(retries):
                try:
                    return view(*args, **kwargs)
                except Error as e:
                    if not _is_occ_error(e):
                        raise  # non-retryable — propagate immediately
                    if attempt == retries - 1:
                        raise  # exhausted retries
                    print(f"OCC conflict, retrying (attempt {attempt+1}/{retries})")
                    time.sleep(random.uniform(0, delay))  # exponential backoff with jitter
                    delay *= delay_factor
        return wrapper
    return decorator
```

Apply to view methods:

```
from django.db.transaction import atomic

@with_retries()
@atomic
def post(self, request, *args, **kwargs):
    # ... write logic ...
```

<a name="SECTION_program-with-dsql-adapter-for-django-settings-py-checklist-for-aurora-dsql"></a>

The following example shows the `settings.py` values to review for Aurora DSQL:

```
INSTALLED_APPS = [
    'your_app',           # add your app
    # remove 'django.contrib.admin', 'django.contrib.auth', and so on
    # unless you have reconfigured them for UUID PKs
]

DATABASES = {
    'default': {
        'ENGINE': 'aurora_dsql_django',
        'HOST':   '{{cluster-id}}.dsql.{{region}}.on.aws',
        'USER':   'admin',
        'NAME':   'postgres',
        'OPTIONS': {'sslmode': 'verify-full'},
    }
}
```

If you turn on persistent connections, set `CONN_MAX_AGE` below 3600 seconds (for example, `3300`). Aurora DSQL closes connections after one hour.

## Adapter features reference
<a name="SECTION_program-with-dsql-adapter-for-django-adapter-features-reference"></a>

The following table lists adapter support for indexes and constraints.


| Capability | Supported | Notes | 
| --- | --- | --- | 
| CREATE INDEX ASYNC | Yes | All index creation uses async syntax | 
| CREATE UNIQUE INDEX ASYNC | Yes | The adapter creates unique constraints as async unique indexes | 
| Foreign key enforcement | Yes | supports\_foreign\_keys = True; the adapter emits REFERENCES constraints in migrations. Aurora DSQL enforces FKs via OCC: conflicts raise OC000 (SQLSTATE 40001), which your application can retry | 
| Deferrable unique constraints | No | Aurora DSQL supports deferral for foreign keys; unique constraints use immediate enforcement. supports\_deferrable\_unique\_constraints = False reflects this platform behavior. | 
| Check constraints | Yes | supports\_table\_check\_constraints is True, so the adapter emits CHECK constraints in model Meta.constraints. For CHECK constraints added to existing tables, inspect the async validation job, because the migration doesn't wait for it | 
| SET CONSTRAINTS | Yes | Supported for foreign keys | 
| Index opclasses | No | The adapter creates standard indexes. | 

The following table lists adapter support for primary keys.


| Capability | Supported | Notes | 
| --- | --- | --- | 
| UUID auto PKs | Yes (default) | AutoField/BigAutoField → uuid \+ gen\_random\_uuid() | 
| Identity/sequence PKs | Yes (opt-in) | USE\_SEQUENCE\_AUTOFIELDS = True | 
| SequenceAutoField | Yes | Custom field for explicit sequence-backed integer PKs | 

The following table lists adapter support for transactions and errors.


| Capability | Supported | Notes | 
| --- | --- | --- | 
| SAVEPOINT | No | The adapter sets the uses\_savepoints and can\_release\_savepoints feature flags to False | 
| OCC error codes | OC000 (data conflict), OC001 (schema conflict) | Catch django.db.Error and retry | 

The following table lists adapter support for Django versions.


| Capability | Supported | Notes | 
| --- | --- | --- | 
| Django 4.2 LTS | Yes | Not applicable | 
| Django 5.x | Yes | 5.0, 5.1, 5.2 LTS |
